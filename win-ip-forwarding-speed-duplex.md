# Настройка временной маршрутизации в Windows и устранение проблем с Auto-Negotiation

Организация временного доступа между изолированными подсетями средствами ОС Windows — стандартная инженерная задача. Ниже разобран типовой случай настройки программного маршрутизатора и устранения неполадок на физическом уровне (L1/L2), когда корректная конфигурация сетевого уровня (L3) не дает результата.

### Исходные данные и постановка задачи

* **Основная сеть:** Офисная локальная сеть `192.168.100.0/24`. Рабочая станция под управлением Windows получает IP-адрес `192.168.100.155`.
* **Целевое устройство:** Система контроллеров на базе Linux с жестко заданным IP-адресом `192.168.1.65`. Изменение адреса устройства и прямой доступ к его интерфейсу невозможны. Программа для работы с контроллерами установлена на указанной Windows-машине.
* **Задача:** Обеспечить временный доступ к Linux-устройству с других рабочих станций в подсети `192.168.100.0/24`. Поскольку доступ для других ПК требуется на короткий срок, внесение изменений в таблицу маршрутизации центрального офисного роутера нецелесообразно.

### Этап 1. Базовая настройка маршрутизации

Для реализации схемы в Windows-ПК была установлена дополнительная сетевая карта. Конфигурация интерфейсов выполнена следующим образом:

1. **Интерфейс 1 (Смотрит в LAN):** `192.168.100.155` (настройки получены по DHCP от офисного роутера).
2. **Интерфейс 2 (Смотрит на Linux-устройство):** Назначен статический IP-адрес `192.168.1.1` с маской `255.255.255.0`. Основной шлюз (Default Gateway) на этом интерфейсе не указывается, чтобы сохранить корректный доступ в интернет через первую сетевую карту.

Для включения функции пересылки пакетов между интерфейсами (IP Forwarding) использована команда PowerShell с правами администратора:

```powershell
Set-NetIPInterface -Forwarding Enabled

```

Так как конфигурация офисного роутера осталась неизменной, маршрут к целевой подсети `192.168.1.0/24` прописывался локально, исключительно на тех компьютерах в сети `100.x`, которым требовался доступ. Команда для cmd (от имени администратора):

```cmd
route -p add 192.168.1.0 mask 255.255.255.0 192.168.100.155

```

### Этап 2. Траблшутинг: отсутствие связи при корректном L3

Несмотря на визуально безупречную конфигурацию, утилита `ping` на адрес `192.168.1.65` упорно возвращала «Превышен интервал ожидания для запроса». Связи не было даже с самого ПК-шлюза. Физическое подключение при этом сомнений не вызывало — индикаторы на портах активно мигали.

Как это часто бывает в подобных ситуациях, первой мыслью стал поиск ошибки в собственных действиях на уровне маршрутизации. Полагая, что где-то закэшировались неверные данные или произошел сбой в таблицах, было потрачено время на классическую зачистку сетевых настроек Windows.

В ход пошли стандартные команды:
Очистка кэша ARP:

```cmd
arp -d *

```

Полная очистка таблиц маршрутизации (чтобы затем прописать нужный маршрут заново):

```cmd
route -f

```

И даже сброс стека TCP/IP:

```cmd
netsh int ip reset

```

Однако перенастройка L3 «с чистого листа» дала ровно тот же результат — глухая изоляция. Брандмауэр отключен, кабель исправен, адреса верны. И в этот момент пришло осознание досадного упущения: если программный уровень настроен идеально, а ARP-запросы уходят в пустоту при физически поднятом линке, значит, мы смотрим не на тот уровень модели OSI. Проблему нужно искать на стыке уровней L1/L2.

**Причина сбоя:**
Разгадка скрывалась в аппаратных особенностях дополнительной сетевой карты (Intel Ethernet Controller I225-V). Этот современный адаптер поддерживает пропускную способность 2.5 Gbps. При подключении к интерфейсу системы контроллеров стандартный механизм автосогласования (Auto-Negotiation) отрабатывал некорректно. Оборудование не могло договориться о скорости и дуплексе: контроллер адаптера считал соединение установленным, но фактически кадры отбрасывались.

**Решение проблемы:**
Потребовалось жестко зафиксировать параметры порта на стороне Windows-машины (процесс показан на скриншоте).

1. Откройте **Диспетчер устройств** (`devmgmt.msc`).
2. В разделе **Сетевые адаптеры** выберите свойства используемой сетевой карты (Intel I225-V).
3. Перейдите на вкладку **Дополнительно** (Advanced).
4. Найдите параметр **Speed & Duplex** (Скорость и дуплекс).
5. Измените значение с `Auto Negotiation` на фиксированное — **`1.0 Gbps Full Duplex`** (или `100 Mbps Full Duplex` в зависимости от порта контроллера).

Сразу после применения настроек и перезапуска интерфейса пинг до `192.168.1.65` прошел успешно, и устройства из локальной сети получили ожидаемый доступ.

### P.S. Отмена маршрутизации (Rollback)

После того как временная необходимость в доступе с *других* компьютеров отпадет, маршрутизацию следует отключить, сохранив при этом связь самой Windows-машины с контроллерами.

**1. Отключение маршрутизации на Windows-ПК:**
В PowerShell от имени Администратора выполните:

```powershell
Set-NetIPInterface -Forwarding Disabled

```

**2. Удаление статических маршрутов на клиентских ПК:**
На компьютерах, где локально прописывался маршрут, откройте командную строку от имени Администратора и выполните:

```cmd
route delete 192.168.1.0 mask 255.255.255.0

```

*Настройки второй сетевой карты на Windows-машине (статический IP 192.168.1.1 и жестко заданная скорость порта) остаются без изменений, так как они необходимы для штатной работы управляющей программы с Linux-системой.*
